# SERENE MANAGEMENT — Security overview

This is an index of the security controls and where each is implemented and verified. Details live in the referenced documents. Audit status and open findings are in [PRODUCTION_READINESS.md](PRODUCTION_READINESS.md).

> **As of the server split (2026-11-12, [SERVER_SPLIT_PLAN.md](SERVER_SPLIT_PLAN.md)):** the backend is a separate Express server and the Next.js app is a pure client. Paths in the table below refer to the pre-split layout: `lib/auth`, `modules/identity` and `modules/access` are now `server/lib`, `server/middlewares` and `server/modules`; `lib/env.ts` is `server/config/env.ts`. What changed in behaviour: the access token is a **Bearer** header value held in client memory (no access cookie, no session-marker cookie); the **refresh token** is the only cookie (`httpOnly`, `SameSite=Strict`, `Path=/api/v1/auth`, `Secure` in production); the CSRF Origin check applies only to the cookie endpoints (`/auth/refresh`, `/auth/logout`) and compares against `CLIENT_ORIGINS` (replaces `APP_URL`); a CORS allowlist (`CLIENT_ORIGINS`) governs browser calls; one active session per user per platform; and resolved sessions and permissions are **cached** (see below).

## Operator responsibilities

- Keep `.env` files (`server/.env`) and backups out of version control and off shared storage; backups are encrypted and kept off the host (OPERATIONS §2).
- Run the application as the runtime role, not as the schema owner (OPERATIONS §4).
- Make instances reachable only through the proxy chain, and set `TRUSTED_PROXY_HOPS` to its exact length (DEPLOYMENT §7).
- On shared workstations, staff sign out at the end of a shift.
- Rotating `AUTH_REFRESH_TOKEN_SECRET` signs everyone out (DEPLOYMENT §8).
- Serve the client and the API from the same site (the refresh cookie is `SameSite=Strict`), and list only your own https origins in `CLIENT_ORIGINS`.
- Operator commands that write are dry runs unless given `--apply --yes --database <name>` (OPERATIONS).

## Known limitations

See PRODUCTION_READINESS §3. Notably:

- refresh-token reuse is detected for one generation only (P2-1, a post-handover enhancement);
- there is no payment-provider integration, so no card data is ever handled (payments are recorded only).
