## 1. System overview

SERENE MANAGEMENT is a multi-property hotel PMS. It is a Next.js 16 client and an Express 5 API server in one repository (npm workspaces), sharing contracts through `@serene/shared`, with a strict internal split in the server:

```text
 Browser (React 19, RTK Query cache, Zustand UI state; access token in memory)
    │  HTTPS, JSON, Authorization: Bearer <access JWT>; refresh token in an httpOnly cookie
    ▼
 client/  Next.js 16 (pure client: pages and layouts, no API routes, no server-side auth)
    │  fetch to NEXT_PUBLIC_API_URL  (CORS allowlist CLIENT_ORIGINS)
    ▼
 server/  Express 5 ── app.ts: requestId → observe → helmet → cors → body limit → cookies → write limit
    │
 server/modules/<feature>/<feature>.routes.ts ── middleware chain: requireAuth → propertyScope → requirePermission → validate → idempotency → controller
    │
 server/modules/<feature>/*.controller.ts ── thin: call one service function, send the envelope
    │
 server/modules/<feature>/*.service.ts ── use cases, business rules, state machines, transactions, audit, events
    │
 server/modules/<feature>/*.repository.ts ── Prisma queries (select shapes, raw SQL for reports)
    │
 PostgreSQL 18 ── constraints, exclusion constraints, triggers = last line of defence

 Optional: Redis (session and permission caches shared by instances; memory fallback)
 Separate process: server/workers/worker.ts (durable job worker, night audit)
 shared/  Zod contracts, types, pure policies, permission catalog, utilities (imported by client and server)
```

Principles, in priority order:

1. **Correct hotel workflows first.** A workflow is complete only when persistence, validation, permissions, audit, inventory, billing and dependent modules are all handled (Guide §52–55).
2. **The server is the authority.** UI checks are convenience; the API's middleware chain and services re-check everything. The database re-checks the most important invariants.
3. **Property isolation by construction.** Property comes from the URL, is authorized per request, is required by every property-scoped service call, and is enforced by composite foreign keys.
4. **Ledgers are append-only.** Financial postings, audit logs and status history are never updated or deleted.
5. **Simple and explicit.** One abstraction per real need. No generic repositories, no event-sourcing framework, no DI container.

## 3. Layering and dependency rules

Three workspaces and one direction of dependency: `client` and `server` import `shared`; they never import each other, and `shared` imports neither.

| Layer                                                                       | May import                                                                                                                                  | Must not import                                              |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `shared/` (schemas, types, policies, permissions, utils)                    | other `shared/` files, `zod`                                                                                                                | Prisma, `node:*`, React, Next, Express, `client/`, `server/` |
| Client UI (`client/app/**`, `client/global/**`)                             | `@serene/shared/...`, `client/global/api`, `client/global/stores`, own route folders                                                        | anything under `server/`, Prisma, Node-only APIs             |
| Routes (`server/modules/*/*.routes.ts`) and controllers (`*.controller.ts`) | `server/middlewares`, `server/lib` (response, validate, controller), the module's validators and service, `@serene/shared/...`              | repositories, `config/prisma`                                |
| Services                                                                    | own repository, other modules' **services** (never their repositories), `config/prisma` (for `$transaction`), audit/events, shared policies | Express (`req`, `res`), `client/`                            |
| Repositories                                                                | `config/prisma`, generated Prisma types                                                                                                     | other modules' tables (call that module's service instead)   |
| Policies (`shared/modules/*/*.policy.ts`)                                   | nothing outside `shared/`; pure functions                                                                                                   | Prisma, I/O                                                  |

Enforcement:

- ESLint `no-restricted-imports` rules in each workspace's `eslint.config.mjs` (`client/`, `server/`, `shared/`), run by `npm run lint`: the client cannot import server code, `shared/` cannot import Prisma, `node:*`, React or `server-only`, and routes and controllers cannot import repositories. `tsconfig` path aliases differ per workspace (`@/…` is `server/…` or `client/…`), so a cross-workspace relative import also fails typechecking.
- Composite foreign keys in PostgreSQL make cross-property references impossible at the data level.
- The earlier `import "server-only"` guard is not needed: client code cannot reach `server/` at all.

**Cross-module calls.** A service may call another module's service within the same transaction by passing the `tx` handle (`Tx` from `server/config/prisma.ts`). Example: `frontDesk.checkIn` → `roomAssignment.assert…(tx)`, `billing.openFolio(tx)`, `rooms.setFrontOfficeStatus(tx)`. There is no event-driven choreography for in-process workflows; events (outbox) exist only for side effects outside the transaction (real-time push, integrations, emails).

## 4. Request lifecycle (server)

Since the server split ([D72–D79](#15-decisions-that-refine-the-guide)) the single `defineRoute` helper is replaced by an Express middleware chain with the same order and the same `RequestContext` semantics. `server/app.ts` first applies, to every request: `requestId` → `observe` (metrics, in-flight tracking) → `helmet` → `cors` (allowlist `CLIENT_ORIGINS`, credentials) → JSON body limit (1 MiB, JSON only) → `cookie-parser` → global write limit (300/min per IP). Routers are mounted under `/api/v1`, health and metrics under `/api`, then a 404 handler and `errorHandler`.

Each route then declares its own chain (Guide §39 order):

```ts
// server/modules/reservations/reservations.routes.ts
router.post(
  "/properties/:propertyId/reservation-rooms/:reservationRoomId/cancel",
  requireAuth, //                           1. authenticate: Bearer JWT → session (cached) → req.ctx
  propertyScope, //                         2. scope: :propertyId + canAccessProperty → PropertyContext
  requirePermission("reservations:cancel"), // 3. authorize (property from path)
  validateParams(reservationRoomParamsSchema), // 4. validate
  validateBody(cancelReservationSchema),
  requireReasonForHighRisk("reservations:cancel"),
  idempotency({ required: true }), //       Idempotency-Key where the command needs it
  controller.cancel, //                     5. call service, 6. envelope
);

// reservations.controller.ts
export const cancel = handleProperty((req) =>
  service.cancelReservation(req.ctx, req.params.reservationRoomId, req.body),
);
```

What each step does, in order:

1. **Request id** (`requestId`): from `x-request-id` or a new UUID; sent back on every response.
2. **Authenticate** (`requireAuth`): reads `Authorization: Bearer`, verifies the JWT (`jose`; `sub`, `org`, `sid`), resolves the session through the session cache (30 s with Redis, 10 s in memory; falls back to one indexed query), then the user's grants through the permission cache. Failure is `401 UNAUTHENTICATED` with a reason code (`TOKEN_MISSING`, `TOKEN_INVALID`, `TOKEN_EXPIRED`, `SESSION_EXPIRED`, `SESSION_REVOKED`, `ACCOUNT_DISABLED`).
3. **Scope** (`propertyScope`): reads `propertyId` from the path, asserts `canAccessProperty`, loads the property's current business date and timezone; `req.ctx` becomes a `PropertyContext`. Organization routes use `requireOrgPermission` instead.
4. **Authorize** (`requirePermission` / `requireOrgPermission`): `hasPermission(access, propertyId, permission)`; high-risk permissions additionally require a reason in the body (`requireReasonForHighRisk`).
5. **Validate** (`validateParams`, `validateQuery`, `validateBody`): Zod schemas from `@serene/shared`, `strict` objects, unknown fields rejected.
6. For state-changing routes: rate limits (`rateLimit(rule)`) and the idempotency key (`idempotency({ required })`). The cookie endpoints (`/auth/refresh`, `/auth/logout`) also check `Origin` (`sameOrigin`); Bearer requests need no CSRF check.
7. The controller calls the service with a `RequestContext`:

```ts
interface RequestContext {
  requestId: string;
  userId: string;
  organizationId: string;
  propertyId: string; // authorized, never taken from the body
  businessDate: string; // "YYYY-MM-DD", property's current business date
  timezone: string; // IANA zone of the property
  ip?: string;
  userAgent?: string;
}
```

8. The controller wraps the result as `{ success: true, message, data, meta? }`; any thrown error reaches `errorHandler`, which answers `{ success: false, message, error: { code, details?, requestId } }` (`server/lib/response.ts`). `AppError(status, message, isOperational, code, details?)` is the thrown type; services keep throwing by code through `appError(code, message, details?)`. Non-operational errors are logged and answered as `INTERNAL_ERROR`. Streaming routes (SSE events, CSV exports, the avatar image) write to `res` directly.

Services never read cookies, headers or the URL, and never see `req` or `res`; they are callable from tests, jobs and the night audit with an explicit context. Data scope helpers `propertyWhere(ctx)` and `organizationWhere(ctx)` (`server/lib/scope.ts`) keep every property- or organization-scoped query filtered.

## 5. Transactions, locking and concurrency

- **Unit of work = one service command = one `prisma.$transaction`** (interactive, `ReadCommitted`). Everything a workflow changes — including the audit record and outbox event — commits or rolls back together (Guide §40).
- **Explicit row locks** on contention points, always taken in a fixed order to avoid deadlocks. As implemented (Phases 2–3; decision D13):
  1. `business_dates` row of the property (`FOR SHARE` for commands, `FOR UPDATE` for night audit)
  2. `reservation_rooms` row being transitioned (`FOR UPDATE`, with the client's `version`)
  3. `stays` row of that reservation room (`FOR UPDATE`, with the client's stay `version`)
  4. `room_type_inventory` rows, ordered by `(room_type_id, stay_date)` (`FOR UPDATE`)
  5. `block_allocations` rows, ordered by `(room_type_id, stay_date, block_id)` (`FOR UPDATE`, Phase 6)
  6. `property_sequences` row (short hold)
  7. `rooms` rows whose occupancy, housekeeping or service status changes — or that are being assigned — ordered by id (`FOR UPDATE`)
  8. `housekeeping_tasks` row (`FOR UPDATE`, with the client's `version`)
  9. `folios` rows being posted to, ordered by id (`FOR UPDATE`)
  10. `payments` row being voided or refunded (`FOR UPDATE`)

  Rates and groups (Phase 6) insert two locks between 3 and 4: the `blocks` row (`FOR UPDATE` for block commands — allocation, status, release; `FOR SHARE` for pickups, so pickups of one block run in parallel and serialize on the inventory cells), then the `rate_plans` chain (`FOR SHARE` while pricing, so a quote never mixes old and new prices; `FOR UPDATE` for rate administration, parent first). Block pickups and release claim their `idempotency_keys` row right after the business date.

  Profile commands (Phase 7) are organization-level and lock their aggregate root first: the `guests` row (profile, preferences, notes, loyalty enrollment — so two enrollments of one guest serialize), the `account_profiles` row (company and its relationships) or the `loyalty_memberships` row (tier, status, points). A reservation's company change locks the `reservations` row before reading its rooms.

  Financial commands (Phase 5) claim their `idempotency_keys` row right after the business date, before any other lock; room-charge posting then locks the reservation room (2), payments take the receipt sequence (6) before the folio (9), and check-out locks the stay's folios after its rooms (7).

  Maintenance commands lock their `maintenance_requests` row right after the business date (the request is the aggregate root), then follow the order above.

- **Optimistic concurrency** for user edits: mutable aggregates carry `version`; updates use `WHERE id = $1 AND version = $2` and return `409 CONFLICT (STALE_VERSION)` when nothing matched.
- **Database guards** catch what slips through: the exclusion constraint on `room_assignments` (no double-booked room), unique partial indexes (one current business date, one open cashier shift per user, one running night audit), check constraints, append-only triggers.
- **Retries**: a command that fails with a serialization/deadlock error (`P2034` / `40001` / `40P01`) is retried up to 3 times with jitter by the transaction helper; business errors are never retried.
- **Idempotency**: payments, postings, check-in, check-out, night audit require an `Idempotency-Key`; the stored response is replayed on retry (`idempotency_keys`).

## 6. Business date and time

- The **business date** (`business_dates`, one current row per property) is the hotel's accounting day. It advances only through night audit. Every posting, payment, status change and report uses it, never `new Date()` (Guide §30).
- **Instants** are stored as `timestamptz` (UTC). **Stay dates and business dates** are `date` columns and travel as `"YYYY-MM-DD"` strings — never converted through JavaScript `Date` in business logic.
- Each property has an IANA `timezone`. Conversion to local time happens only at the display boundary (UI) and when interpreting local wall-clock policies (cancellation deadline "18:00 local", ETA).
- While a night audit is running, the business date is `IN_AUDIT` and posting commands fail with `423 BUSINESS_DATE_LOCKED`.

## 7. Frontend architecture

### 7.1 Routing and layouts

The client is a pure client of the API: it has no API routes and its server side reads no session (the access token lives in browser memory, not in a cookie Next.js can see). `client/proxy.ts` only sets the per-request CSP nonce and security headers (`connect-src` includes the API origin).

- `app/(auth)` — public pages (login, password reset). Minimal layout.
- `app/(workspace)` — authenticated frame. Its layout renders the **client auth guard** (`WorkspaceAuthGuard`): on load it calls `/auth/refresh` once (cookie) to obtain an access token, then `GET /me` (`useMeQuery`), then renders the shell (navigation, top bar with property switcher, business date, global search, user menu) or redirects to `/login?reason=<code>` with the server's message. `useRequireAuth` and `PermissionGate` are UI conveniences, never the security boundary.
- `app/(workspace)/[propertyCode]/…` — every property-scoped screen. The **selected property lives in the URL**, so deep links, browser tabs on different properties and RTK Query cache keys are all property-correct. Its layout resolves `propertyCode → propertyId` from the `me` payload on the client and renders a permission-denied state if the user lacks access.
- `app/(workspace)/organization/…` — organization-wide administration (users, roles, properties, profile configuration); guarded the same way from `me`.
- `app/page.tsx` redirects on the client. Reserved segment names (`organization`, `login` …) are rejected as property codes by validation.

### 7.2 Route-local colocation (Guide §33)

Everything belonging to one route stays inside that route. Folders that Next.js must not treat as routes are prefixed with an underscore:

```text
client/app/(workspace)/[propertyCode]/reservations/
├── page.tsx                      # composes components; no business logic
├── [reservationId]/page.tsx
├── new/page.tsx
├── _components/                  # ReservationSearchPanel, ReservationSummary, NightsGrid …
├── _hooks/                       # useReservationFilters …
└── _lib/                         # form schemas composed from @serene/shared/modules/reservations, route-local helpers
```

Promotion rule (Guide litmus test): code moves to `client/global/` only when a **second route** needs it:

| Needed by 2+ routes | Promote to                                                           |
| ------------------- | -------------------------------------------------------------------- |
| UI component        | `global/components/ui/` (primitive) or `global/components/<domain>/` |
| Hook                | `global/hooks/`                                                      |
| RTK Query endpoints | `global/api/endpoints/<feature>Api.ts` (`baseApi.injectEndpoints`)   |
| Store               | `global/stores/`                                                     |
| Zod contract        | already in `shared/modules/<domain>/<domain>.schema.ts`              |
| Types               | `shared/modules/<domain>/<domain>.types.ts` or `shared/types/`       |

Components stay below ~250 lines; pages compose; business rules live in `shared/modules/*/*.policy.ts` (shared with the server) or on the server.

### 7.3 State

| Kind of state   | Tool                                                           | Examples                                                                                       |
| --------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Server data     | **RTK Query** (single `baseApi`, `injectEndpoints` per domain) | reservations, rooms, folios, availability, reports, users                                      |
| Client/UI state | **Zustand**                                                    | navigation drawer, command menu, selected rows, open drawers, multi-step drafts, table density |
| URL state       | search params                                                  | filters, sort, page, selected date range (shareable)                                           |
| Form state      | React Hook Form + Zod resolver (recommended, see §16)          | reservation form, check-in form                                                                |

Rules:

- Server records never go into Zustand (Guide §36). A Zustand store may hold **ids** (selected reservation ids), never copies of records.
- Every parameter that changes a result is part of the RTK Query argument (so of the cache key): property id, filters, date range, cursor.
- Tags: `providesTags` per entity (`{ type: "Reservation", id }`) plus list tags (`{ type: "Reservation", id: "LIST" }`); mutations invalidate precisely.
- Real-time events (§10) translate into `baseApi.util.invalidateTags`. `baseApi` (`client/global/api/baseApi.ts`) adds the Bearer header and `X-Client-Platform: web`, unwraps the envelope, shares one in-flight refresh on 401, and retries 429/503 with backoff.
- Optimistic updates only for low-risk, reversible UI-local changes (e.g. housekeeping task progress), never for money or inventory.
- `store/property.store.ts` is intentionally **not** created: the selected property is in the URL, and the session user comes from `GET /me` (server data → RTK Query). `global/stores/auth.store.ts` (D74, superseding D2) exists but holds only the in-memory access token, its expiry and the boot status (`booting | authenticated | anonymous`), never user records.

### 7.4 Error, loading and permission states

Every data view renders five states: loading (skeleton matching layout), empty (with next action), error (message + retry + `requestId`), permission denied (explains which permission is missing), and data. Mutations show inline field errors from `VALIDATION_FAILED.details.fields` and toast business-rule errors by `code`.

## 8. Design system foundation

Implemented tokens: `app/globals.css`; primitives: `components/ui/`; shell: `components/workspace/AppShell.tsx`. The full rules (tokens, typography, status semantics, components, states, responsive, accessibility, dark mode) and the audit behind them are in **[DESIGN_SYSTEM.md](DESIGN_SYSTEM.md)** (UI/UX overhaul, Batch 0), which supersedes the values in this table where they differ.

**Direction**: light, Nginap-inspired hospitality PMS with operational density. ## 9. Security architecture

| Concern            | Design                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authentication     | Email + password. Access token = short-lived JWT (HS256 via `jose`, 15 min; claims `sub`, `org`, `sid`); refresh token = 256-bit opaque random value, stored only as SHA-256 in `auth_sessions`, 14 days, **rotated on every refresh** with reuse detection (presenting a previous token revokes the session).                                                                                                                                                                                                                                                                                                                                                                                       |
| Token transport    | The access token is sent as `Authorization: Bearer` and lives only in client memory (Zustand), never in `localStorage`, a cookie or any JS-readable storage (D74, superseding D56's access cookie). The refresh token is an `httpOnly`, `SameSite=Strict`, `Path=/api/v1/auth` cookie (`Secure` and `__Secure-` prefixed in production) and is the only cookie the API sets. On page load the client calls `/auth/refresh` once to restore the session. One active session per user per platform (`X-Client-Platform: web \| mobile`): a new login revokes the user's other sessions on that platform.                                                                                               |
| Password hashing   | argon2id (`@node-rs/argon2`, OWASP parameters: m = 19 MiB, t = 2, p = 1). Minimum length 12, breached-password check recommended (Phase 1 open item).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Lockout            | 5 consecutive failures → lock 15 min (doubling, max 1 h since Phase 10, D45); attempts admitted under a row lock; `users.failed_login_count`, `locked_until`; audited. Uniform error message for unknown email vs wrong password.                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Password reset     | Administrator-issued single-use token (HMAC stored), 30 min expiry, delivered as a link with the token in the URL fragment; all sessions revoked on issue and on use; self-service change revokes every other session (D47).                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Session marker     | Removed (D74). It existed so `proxy.ts` could tell whether a refresh cookie probably existed; Next.js no longer gates routes, so the `sm_s` / `__Host-sm_s` cookie is no longer set.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Route protection   | The client guards routes in its layouts (boot refresh → `me` → render or redirect to `/login`), which is a usability feature only. **Every API route authenticates and authorizes independently** through its middleware chain (`requireAuth` → `propertyScope` → `requirePermission`); the client is never trusted for authorization (Guide §27).                                                                                                                                                                                                                                                                                                                                                   |
| Session refresh    | RTK Query `baseApi`: on `401`, one shared in-flight call to `/auth/refresh`, then retry; on failure, redirect to `/login?reason=<code>` showing the server's message. 401 reason codes: `TOKEN_MISSING`, `TOKEN_INVALID`, `TOKEN_EXPIRED`, `SESSION_EXPIRED`, `SESSION_REVOKED`, `ACCOUNT_DISABLED`.                                                                                                                                                                                                                                                                                                                                                                                                 |

| Input validation   | Zod on every param/query/body; `.strict()` objects; server-side only authority (Guide §37).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| SQL injection      | Prisma parameterized queries; raw SQL only through tagged `Prisma.sql` templates.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Rate limiting      | Login: per trusted IP + per account (D45); refresh and reset completion: per trusted IP; password change: per user. API: per user. Client IP from trusted proxy hops only (D44). ## 10. Real-time operations

- Every state change that other screens care about writes an `outbox_events` row **inside its transaction** (`room.status_changed`, `reservation.checked_in`, `folio.posted`, `housekeeping.task_updated` …).
- A relay publishes pending events to Server-Sent Events streams: `GET /api/v1/properties/{id}/events` (one stream per open workspace). Clients map event types to RTK Query tag invalidations.
- Phase 7 starts with a single-instance relay (poll outbox every 1 s, or PostgreSQL `LISTEN/NOTIFY`). Multi-instance deployment needs a shared fan-out (PostgreSQL `LISTEN/NOTIFY` per instance or Redis pub/sub) — see open questions.
- Polling (RTK Query `pollingInterval`) is the fallback for screens without SSE.
- **As of the server split (D74)**: the stream is served by Express (`GET /api/v1/properties/{id}/events`, `server/modules/realtime`). The client reads it with `fetch` and the Bearer header (an `EventSource` cannot send headers), on a 401 it refreshes the session and reconnects; the stream ends with `event: reauth` when access changes or the token expires. Events remain refetch hints, never data.
- **As implemented (Phase 9, D35)**: the transactional writer and nine event types exist; there is no relay or SSE stream yet, so screens keep polling and events stay `PENDING`.

## 11. Integration architecture

- Integrations never write core tables directly. They call module services (inbound) or consume outbox events (outbound).
- Each external system gets an adapter folder `modules/integrations/<system>/` implementing a narrow port defined by the consuming module, e.g. `payments` defines `PaymentProvider { createPaymentSession, capture, refund, void }`; `front-desk` defines `DoorLockProvider { issueKey }`.
- External identifiers are stored as references (e.g. `reservations.external_reference`, `payments.gateway_reference`); a generic `external_mappings` table is added when the first two-way integration (channel manager) arrives.
- Planned adapters: payment gateway (first), channel manager/booking engine, POS posting interface, accounting export (GL mapping on transaction codes), door locks, SMS/WhatsApp/email, ID scanning.
- **As implemented (Phase 9, D40)**: `modules/integrations/` holds the event catalog, envelope and publisher contract only; no adapter, key, webhook or inbox exists.
- Sales & catering is a **separate bounded context** (Guide §23): it will own leads, events, function spaces and catering orders, and interact with PMS only through `groups`/`blocks` (room blocks) and `billing` (event folio) services.

## 12. Performance architecture

**High-volume tables** (row growth drivers for a 300-room hotel, per year): `folio_items` (~1–3 M), `audit_logs` (~2–5 M), `room_status_history` (~0.5 M), `reservation_room_nights` (~0.1 M), `housekeeping_tasks` (~0.1 M), `outbox_events` (~1 M, purged), `payments`, `stays`, `reservations`. Chains multiply by property count.

| Risk                                    | Mitigation                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Loading large datasets into the browser | Every list endpoint is paginated (cursor default, max 200); grids request a bounded window (e.g. room rack = rooms × 14 days).                                                                                                                                                                                                                                                                                                   |
| Expensive reports                       | SQL aggregation (`GROUP BY` in PostgreSQL); closed dates read `daily_statistics` snapshots written by night audit; row-level reports capped at 20 000 rows; heavy report keys limited per process (D65). Measured too short to need background export files (≤ 2.8 s). `EXPLAIN (ANALYZE, BUFFERS)` reviewed for every report query before merge.                                                                                |
| Availability search                     | O(room types × nights) read of `room_type_inventory` counters + sparse `restrictions`; no scanning of reservations.                                                                                                                                                                                                                                                                                                              |
| Guest search                            | `pg_trgm` GIN index on normalized `search_name`; exact indexes for email, phone, confirmation number, room number.                                                                                                                                                                                                                                                                                                               |
| N+1 queries                             | Repositories return complete view shapes with Prisma `select`/`include` or one raw SQL query; lint/review rule: no query inside loops; batched `IN (…)` lookups.                                                                                                                                                                                                                                                                 |
| Unbounded parallelism                   | No `Promise.all` over unbounded arrays of queries; bulk writes use `createMany` / `INSERT … SELECT`.                                                                                                                                                                                                                                                                                                                             |
| Contention                              | Short transactions; inventory rows locked in fixed order; night audit uses set-based SQL (one `INSERT … SELECT` for room charges, not per-room loops).                                                                                                                                                                                                                                                                           |
| Table growth                            | Plan monthly partitioning of `audit_logs` and yearly partitioning of `folio_items` by `business_date` before they exceed ~50 M rows; outbox purge after publish + 7 days.                                                                                                                                                                                                                                                        |
| Caching                                 | RTK Query short caches + tag invalidation + SSE. Server-side caching only for reference data (room types, codes, transaction codes) with explicit invalidation on settings change. No cache for money or inventory. Exception: results computed only from closed business dates are immutable and cached with stale-while-revalidate and single flight (`server/lib/report-cache.ts`, key prefix `rpt:v1:`; see SCALABILITY.md). |
| Connections                             | One PrismaClient per process with `@prisma/adapter-pg` pool; a pooler (PgBouncer, transaction mode) in production.                                                                                                                                                                                                                                                                                                               |

## 14. Observability and error handling

- Structured JSON logs (request id, user id, property id, route, duration, error code); `console.error` only for `INTERNAL_ERROR` with stack.
- `x-request-id` returned on every response and shown in UI error states so staff can quote it.
- Night audit writes per-step results to `night_audit_steps`.
- Operations (Phase 10 batch 3): backups, restore drill, migration policy, retention, database roles, pool settings, scheduling and CI are described in [OPERATIONS.md](OPERATIONS.md) (D50–D53).
- Health: `/api/health/live` (process only, no database) for liveness, `/api/health/ready` (`SELECT 1` with a 2 s timeout, 503 without details on failure) for readiness; `/api/health` is a readiness alias ([DEPLOYMENT.md](DEPLOYMENT.md) §6).

## 16. Open architectural questions

Decisions needed from the product owner before or during the named phase:

1. **Payment gateway(s)** (Phase 6): which provider(s) for Pakistan/GCC (e.g. local acquirers vs Stripe/Checkout.com)? Determines tokenization UX and whether card-present terminals are needed.
2. **Fiscal/tax compliance** (Phase 6): which jurisdictions? FBR/PRA POS integration in Pakistan, ZATCA e-invoicing in KSA, UAE VAT? Affects invoice numbering, QR codes and credit-note rules.
3. **Rate limiting & real-time fan-out store** (Phase 1/7): rate limits settled on PostgreSQL (D59); for real-time fan-out, approve Redis in production or stay PostgreSQL-only (`LISTEN/NOTIFY`) for simpler hosting? As of the server split Redis is **supported but optional** (D75): it backs the session and permission caches only; rate limits and real-time fan-out stay on PostgreSQL, so Redis can be added later without changing either. Read replicas: readiness prepared, enable only on the conditions of SCALABILITY §35.9 (D67).
4. **Hosting target**: single VM/container with PostgreSQL, managed PostgreSQL + container platform, or Vercel + managed PostgreSQL? Affects SSE (long-lived connections), background jobs and scheduled night audit.
5. **Automatic night audit**: may the audit run on a schedule, or always be started by a user? (Default: user-started, with scheduled reminder.)
6. **Headless UI library**: React Aria Components (recommended: best-in-class accessibility, RTL and date pickers) vs Radix UI + separate date picker.
7. **Urdu typography**: Naskh-style (IBM Plex Sans Arabic, dense, recommended for operational screens) vs Nastaliq (traditional, much taller lines)?
8. **Housekeeping attendants without logins**: confirm that attendants may exist without user accounts (modelled) and that supervisors update on their behalf.
9. **Guest profile sharing across properties**: fully central (modelled), or should some properties in an organization be isolated from each other's guest data?
10. **Row-level security**: add PostgreSQL RLS on `property_id` as defense in depth (requires setting `app.property_id` per transaction), or rely on service scoping + composite FKs (current design)?
11. **Data retention**: how long to keep audit logs, guest documents, cancelled reservations; privacy law obligations (PDPA/GDPR for foreign guests)?
12. **Channel manager** (Phase 12): which provider? Determines whether availability/rates must be pushed in real time from Phase 4 onward.
13. **Currency**: single property currency with foreign-currency payments (modelled), or true multi-currency folios?
