## 1. Conventions

| Topic         | Convention                                                                                                                                                                                                                                   |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Names         | Tables `snake_case` plural (`reservation_rooms`); columns `snake_case`; Prisma models PascalCase, fields camelCase via `@map`. Enum types `snake_case`.                                                                                      |
| Primary keys  | `uuid` generated as **UUIDv7** (`@default(uuid(7))`): time-ordered → B-tree locality, no hot-spot sequence, safe to expose. Join tables use composite PKs.                                                                                   |
| Timestamps    | `created_at`, `updated_at` (`timestamptz(3)`, UTC). Domain instants (`checked_in_at`, `posted_at` …) also `timestamptz`.                                                                                                                     |
| Dates         | Business and stay dates are `date` (`business_date`, `stay_date`, `arrival_date`). Ranges are half-open `[from, to)` unless named `start/end` (inclusive, documented per column).                                                            |
| Money         | `numeric(19,4)` + `char(3)` ISO currency on the same row. Never float. Rounded to the currency's `minor_units` at posting time. Exchange rates `numeric(18,8)`.                                                                              |
| Quantities    | `numeric(12,3)` for posting quantities, `int` for counts.                                                                                                                                                                                    |
| Enums         | PostgreSQL enums for closed sets that code branches on (statuses, kinds). Configurable sets are tables (block statuses, reason codes, market codes).                                                                                         |
| Status fields | Every lifecycle entity has an explicit `status` enum plus timestamp/actor columns for key transitions (`cancelled_at`, `cancelled_by_id` …).                                                                                                 |
| Concurrency   | `version int` on mutable aggregates (Reservation, ReservationRoom, Room, Folio, Stay, Guest, AccountProfile, Block, HousekeepingTask, MaintenanceRequest, RatePlan, Payment, Commission).                                                    |
| Actor columns | `*_by_id uuid` without FK (users are never deleted; the audit log is authoritative). Real relations exist where the user is an operational party: role assignments, sessions, cashier shifts, attendants, maintenance assignee, sales owner. |
| JSON          | Only for snapshots and unstructured payloads: audit before/after, invoice bill-to/lines, outbox payload, night audit summaries. Never for queryable business fields.                                                                         |

## 2. Property scoping

- Every property-scoped table has `property_id NOT NULL`.
- Property-scoped parents expose `UNIQUE (property_id, id)`, and property-scoped children reference them with **composite foreign keys** `(property_id, x_id) → parent(property_id, id)`. A row can therefore never reference a room type, rate plan, folio, etc. of another property — proven by `tests/db/constraints.test.ts` ("property isolation").
- Organization-scoped tables (`guests`, `account_profiles`, `groups`, `users` …) carry `organization_id`; services always filter by the caller's organization.
- Hot query indexes lead with `property_id` so every operational query is a narrow index range.

## 3. Soft delete and retention

| Category                                                                                  | Strategy                                                                                                                          |
| ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Configuration (room types, rate plans, codes, transaction codes, packages …)              | Never deleted once referenced: `status = INACTIVE`. FKs are `ON DELETE RESTRICT`.                                                 |
| Profiles (`guests`, `account_profiles`)                                                   | `deleted_at` soft delete; `MERGED` status with `merged_into_id`; `ANONYMIZED` for privacy erasure (PII blanked, statistics kept). |
| Notes, attachments                                                                        | `deleted_at`.                                                                                                                     |
| Reservations, stays, folios, payments, invoices                                           | Never deleted; state changes only (cancelled, voided, credited).                                                                  |
| Ledgers & history (`folio_items`, `audit_logs`, `room_status_history`, `cash_movements`)  | Append-only, enforced by triggers.                                                                                                |
| Transient (`outbox_events`, `idempotency_keys`, `auth_sessions`, `password_reset_tokens`) | Purged by scheduled jobs after expiry.                                                                                            |
| Child rows owned by a parent (contacts, addresses, allocations, role permissions)         | `ON DELETE CASCADE` from the parent.                                                                                              |

## 5. Integrity rules (database level)

Implemented in `20260924000100_constraints` unless noted as schema-level:

| Rule                                                                                                                                              | Mechanism                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| No reference across properties                                                                                                                    | Composite FKs (schema)                                                                           |
| One current business date per property; `is_current ⇔ status ≠ CLOSED`; closed dates frozen                                                       | Partial unique + check + trigger `serene_business_date_guard`                                    |
| No double-booked room                                                                                                                             | Exclusion constraint `room_assignments_no_overlap` (btree_gist, `daterange`, `occupancy_key <>`) |
| No overlapping OOO/OOS; no double hold                                                                                                            | Exclusion constraints `room_service_blocks_no_overlap`, `room_holds_no_overlap`                  |
| Valid stay dates, party, day-use flag, discount range, cancel/no-show consistency                                                                 | Checks on `reservation_rooms`                                                                    |
| Non-negative inventory counters, allocations, prices, policies                                                                                    | Checks                                                                                           |
| Restriction value presence matches type                                                                                                           | Check                                                                                            |
| Derived-rate consistency; no self-parent                                                                                                          | Checks                                                                                           |
| Folio owner consistency; balance equation                                                                                                         | Checks                                                                                           |
| Ledger consistency (corrections reference originals, transfers paired, taxes have a parent, payments link a payment/refund, FX triple)            | Checks on `folio_items`                                                                          |
| One reversal per item                                                                                                                             | Partial unique (schema)                                                                          |
| Append-only: `audit_logs`, `folio_items`, `room_status_history`, `cash_movements`                                                                 | Trigger `serene_reject_mutation` (SQLSTATE `SM001`)                                              |
| Invoices immutable except ISSUED → CREDITED                                                                                                       | Trigger `serene_invoice_guard`                                                                   |
| No postings into CLOSED folios                                                                                                                    | Trigger `serene_folio_item_insert_guard` (SQLSTATE `SM002`)                                      |
| Payments positive; refunds ≤ payment; deposits linked to a reservation; card last4 digits only                                                    | Checks                                                                                           |
| One OPEN cashier shift per user & property; one RUNNING night audit; one live HK task per room/date/type; one OPEN discrepancy per room/date/type | Partial uniques (schema)                                                                         |
| Role scope ⇔ property id                                                                                                                          | Check                                                                                            |

Custom SQLSTATEs: `SM001` (immutable/append-only violation), `SM002` (closed folio), `SM003` (rate-plan derivation or block pickup guard, Phase 6). The HTTP layer maps them to `BUSINESS_RULE_VIOLATION` (mapping completed in Phase 1, see API_CONVENTIONS.md §5).

### Phase 2 notes

- **Inventory counters**: `room_type_inventory` rows are created on demand (`INSERT ... ON CONFLICT DO NOTHING`) and locked `FOR UPDATE` in `(room_type_id, stay_date)` order by every inventory-changing command; `sold`, `physical_rooms` and `out_of_order` are rewritten from the source rows in the same transaction (see DOMAIN_MODEL.md §5.3).
- **Document numbers**: `property_sequences` rows `confirmation` (starts at 100000, no prefix) and `cancellation` (starts at 1000, prefix `X`) are allocated with `UPDATE ... RETURNING` inside the booking transaction: gap-free and safe under concurrency (verified by a concurrent-booking integration test).
- **Known upstream warning**: under concurrent interactive transactions `pg` 8.x prints a DeprecationWarning (client.query() when the client is already executing a query). It originates in Prisma 7's driver-adapter query interpreter, not in application code; queries are still serialized correctly. Revisit on the next Prisma upgrade.
- **Room-level double booking** is prevented by the `room_assignments_no_overlap` exclusion constraint; the API maps its `23P01` to `409 CONFLICT`.

### Phase 3 notes

- **Stays** are created by check-in and are the operational record of an occupancy (1:1 with a reservation room). `stays_one_in_house_per_room` makes double occupancy impossible at the database level, including the case the assignment exclusion constraint cannot see: a departing guest who has not checked out yet while the next guest's assignment starts on the same day. It will be replaced by an occupancy-key-aware rule when share-with is built.
- **Room assignments are history**: a room move or check-out releases the active assignment and truncates `to_date` to the business date, so released rows record the nights actually spent in each room; the exclusion constraint only considers active rows.
- **Room status** changes made by the front desk (front office VACANT/OCCUPIED, housekeeping → DIRTY on departure or move) write `room_status_history` (append-only) with source `CHECK_IN`, `CHECK_OUT` or `ROOM_MOVE` in the same transaction.

### Phase 4 notes

- **Reused tables**: `housekeeping_tasks`, `housekeeping_task_types`, `housekeeping_attendants`, `maintenance_requests`, `maintenance_activities`, `maintenance_categories`, `room_service_blocks`, `room_status_history` were modelled in Phase 0; Phase 4 adds only the columns and guards above.
- **Service blocks** are the source of truth for out of order / out of service; `room_service_blocks_no_overlap` allows one live block per room and night. Out-of-order placement and release lock the room type's inventory cells and rewrite their counters (`out_of_order`).
- **Room row lock**: every command that puts a guest into a room, assigns a room, blocks it or changes its housekeeping status locks the `rooms` row FOR UPDATE, after inventory and sequence locks (ARCHITECTURE §5, D15).
- **Room status history** now records the reason of the change (cleaning task, inspection result, block reason, correction comment).

### Phase 5 notes

- **Reused tables**: `folios`, `folio_items`, `transaction_code_groups`, `transaction_codes`, `tax_rules`, `transaction_code_taxes`, `payment_methods`, `payments`, `refunds`, `reason_codes`, `property_sequences`, `idempotency_keys` were modelled in Phase 0; Phase 5 adds only the columns, constraints and triggers above. Invoices, routing, cashier shifts, cash movements, card authorizations and deposit requests are untouched.
- **Totals by trigger**: `folio_items_apply` (AFTER INSERT) checks that the line's currency equals the folio's, that a `REVERSAL` negates its original exactly and that `ADJUSTMENT`s never exceed or add to it, then adds the amount to `charges_total` (non-payment codes) or `credits_total` (codes of a PAYMENT group), to `balance`, bumps `version` and reopens a SETTLED folio. `folios_guard` rejects writes to the totals except from that trigger (`pg_trigger_depth() > 1`), non-zero totals on insert, changes of ownership/currency and deletes.
- **Deterministic postings**: system postings (room night, package component) carry `posting_key`; the unique index `(property_id, posting_key)` makes a duplicate posting impossible even if two runs raced.
- **Money**: every amount is `NUMERIC(19,4)` holding values rounded to the currency's minor units (`currencies.minor_units`); rates of tax rules are percent `NUMERIC(19,4)` (16% = `16.0000`).
- **Idempotency**: `idempotency_keys (user_id, key)` rows are inserted inside the command transaction (`INSERT … ON CONFLICT DO UPDATE … WHERE expires_at < now()`), so a concurrent duplicate waits on the uncommitted row and then replays the stored response.

- **Reused tables**: `rate_plans`, `rate_seasons`, `rate_season_amounts`, `rate_plan_room_types`, `rate_plan_packages`, `packages`, `package_components`, `reservation_packages`, `restrictions`, `groups`, `blocks`, `block_statuses`, `block_allocations` were modelled in Phase 0. Phase 6 adds only the migration above; no pricing, package or group table was duplicated.
- **Blocked inventory is derived**: for every DEDUCT block, `blocked = Σ max(0, allocated − released − picked)` per room type and night, where _picked_ counts the deducting nights of reservation rooms with that `block_id` (RESERVED, IN_HOUSE, CHECKED_OUT). `room_type_inventory.blocked` and `block_allocations.picked_up` are caches rewritten under the inventory lock, like `sold` (D12).
- **Restrictions** are rows per stay date and scope (house, room type, rate plan, both). A set or clear replaces the rows of that scope and type in one transaction under `pg_advisory_xact_lock(hashtext('restrictions:' || property_id))`.
- `SM003` is mapped to `BUSINESS_RULE_VIOLATION` (422) by the HTTP layer.

## 6. Transaction boundaries

| Command                      | Rows locked (in order)                                                       | Written in the same transaction                                                                                                                                                   |
| ---------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Create / modify reservation  | business date (share), inventory rows (update), block allocations, sequences | reservation, rooms, nights, guests, inventory counters, allocations pickup, deposit requests, audit, outbox                                                                       |
| Cancel / no-show / reinstate | business date, inventory rows, reservation room                              | status, cancellation number, counters, assignments released, penalty posting (folio), audit, outbox                                                                               |
| Assign / move room           | reservation room, room(s)                                                    | assignments (release + create), reservation_room.room_id, stay.room_id, room statuses, HK task, audit, outbox                                                                     |
| Check-in                     | business date, reservation room, room                                        | stay, status, room FO status, folio(s) window 1..n, deposit transfer, card authorization record, audit, outbox                                                                    |
| Post charge                  | business date, folio(s) (after routing)                                      | folio items (+ generated taxes), folio totals, cashier movement (paid-out), audit, outbox                                                                                         |
| Payment / refund             | business date, folio, payment                                                | payment/refund, folio item, folio totals, cash movement, receipt number, audit, outbox (gateway call happens **before** the transaction with idempotent reference; see workflows) |
| Check-out                    | business date, reservation room, folios, room                                | invoices, folio status, stay, reservation status, room FO/HK status, HK departure task, guest statistics, commission, audit, outbox                                               |
| Night audit (commit phase)   | business date (update), then set-based writes                                | room & tax, packages, fixed charges, no-shows, inventory release, HK status roll, statistics snapshot, date close + next date open, run/steps, audit                              |

## 7. High-volume tables and growth plan

| Table                     | Driver                                                    | Plan                                                                                                       |
| ------------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `folio_items`             | every posting + taxes                                     | Indexed by property/business date/code for reports; yearly partitions by `business_date` beyond ~50 M rows |
| `audit_logs`              | every change                                              | Monthly partitions by `created_at`; archive to cold storage per retention policy                           |
| `room_status_history`     | every status change                                       | Monthly partitions if needed; 2-year hot retention                                                         |
| `reservation_room_nights` | nights × rooms                                            | Indexed `(property_id, stay_date, room_type_id)`                                                           |
| `room_type_inventory`     | room types × horizon (e.g. 30 × 730 = 22 k rows/property) | Rolling horizon maintained by night audit                                                                  |

| `outbox_events`           | every event                                               | Purge 7 days after publish                                                                                 |

Partitioning is introduced by a dedicated migration when monitoring shows the need; primary keys already include no assumptions that would block it (UUIDv7 + partition key will be added to the PK at that time).

## 8. Reporting data

- **Open/current date**: live SQL aggregation over indexed tables.
- **Closed dates**: `daily_statistics` and `daily_room_type_statistics` written by night audit (rooms available/sold/OOO/OOS/comp/house use, arrivals, departures, stayovers, no-shows, cancellations, walk-ins, guests, room/package/other revenue, tax, payments). ADR, RevPAR, occupancy are computed from these components in the query, never stored.
- Financial reports read `folio_items` by `business_date` and transaction code → bucket.

## 9. Seed strategy

- `prisma/seed/index.ts` (implemented): idempotent reference data — currencies, the permission catalog (synchronised from `lib/permissions/catalog.ts`), system role templates.
- From Phase 1, `SEED_DEMO=true` adds a deterministic demo organization with two properties (e.g. a mountain resort and a city hotel), then each phase extends it: floors, room types, rooms (Phase 2), guests/companies/agents (3), rates/packages (4), reservations across past/current/future dates (5), folios/payments (6), in-house guests (7), housekeeping tasks & maintenance requests (8). The demo dataset is generated **through the domain services** so it always satisfies the same rules as real data.

## 10. Migration workflow

1. Edit `prisma/schema/*.prisma`.
2. `npm run db:migrate -- --name <change>` (creates SQL); review the SQL.
3. Rules Prisma cannot express go into the same or a follow-up migration file by hand, and into §5 of this document.
4. `npm run test:db` must pass; `prisma migrate diff --from-config-datasource --to-schema prisma/schema` must be empty on a migrated database.
5. Never edit an applied migration; never change schema without a migration (Guide §54). The Phase 0 baseline may be squashed once before the first production deployment.
